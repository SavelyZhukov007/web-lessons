Основание: локальная main и origin/main синхронизированы на 5f99945, 15 октября 2026. Исполнителей назначает руководитель. Дедлайн нового этапа согласовать отдельно: прежнее 14 октября уже прошло.

## Задача 1 — Завершить серверную логику расписания и запрет конфликтов

Не переписывать готовые модели, API и генератор недели. Подключить существующий модуль conflicts к созданию/изменению регулярных занятий и переносов; проверить отмену исключений и изменение руководителя/активности кружка, если они возвращают занятость или создают новые пересечения.

Соседние интервалы допустимы. Конфликт: одна дата/день и пересечение времени при общей аудитории или руководителе. Отмена освобождает время, перенос занимает новое время и аудиторию. Исключать редактируемое событие, не всю серию. Исправить обработку отменённого candidate в find_conflicts либо обеспечить явно протестированное исключение в вызывающем сервисе.

Согласовать и описать область действия регулярного расписания: в текущей модели нет дат начала/окончания серии. Нельзя ограничить проверку текущей неделей и пропустить конфликт следующей. Для повторяющихся занятий проверять недельные интервалы, для конечного набора исключений — затронутые исходные и целевые даты с их фактическими событиями. Если для этого нужна граница учебного периода, решение вынести руководителю и явно закрепить.

Не сохранять частично ошибочные изменения. Возвращать 409 с объяснением: аудитория/руководитель, конфликтующее занятие и время. Согласовать формат ошибки с интерфейсом админки.

Проверить публичное API: поиск по русскому названию без учёта регистра (SQLite ilike не гарантирует Unicode case folding), допустимые параметры фильтров, ближайшие изменения без старых исключений. Сохранить форматы текущих ответов.

Где работать: backend/app/services/, backend/app/routers/public.py; административные обработчики занятий, кружков и исключений в routers/admin.py; отдельные тесты test_conflict_integration.py. Код авторизации и frontend не менять.

Результат: сервер отклоняет конфликтующие изменения, корректные сохраняет; расписание публично соответствует данным; автоматические тесты граничных сценариев.

## Задача 2 — Сделать публичный интерфейс и подключить к реальному API

Закончить три страницы: расписание, список кружков, страница кружка. Сначала подготовить короткие макеты телефона и компьютера, согласовать один общий стиль, затем верстать по экранам. Не ждать завершения всего дизайна для передачи первого экрана.

Главная: недельное расписание Пн–Сб, выбор недели и возврат к текущей, поиск, совместные фильтры по направлению/дню/руководителю/аудитории и их сброс. Компьютер — читаемая недельная сетка; телефон — удобный дневной список/переключение дней. Отмена/перенос обозначаются текстом; видны время, аудитория и руководитель.

Список: активные кружки, поиск и направление, карточки и переходы. Страница кружка: описание, направление, руководитель/контакты, все регулярные занятия с аудиториями, ближайшие изменения. Обработать 404 и скрытый кружок.

Получать данные через frontend/js/api.js и fetch; подключить реальные GET-маршруты. Расписание формирует backend. Явный режим моков оставить только для разработки; не подменять ими API-ошибки. Обработать загрузку, пустой результат, ошибку и повторный запрос; при быстрых переключениях устаревший ответ не должен заменять новый.

Разделить общие стили и стили публичных страниц, согласовать с админкой общие цвета/кнопки/поля. Не выводить пользовательский текст через innerHTML. Проверить клавиатуру, подписи полей, длинные названия и телефон от 360px.

Где работать: frontend/index.html, clubs.html, club.html, frontend/js/ публичной части, css/public.css, css/common.css; макеты docs/design/public/. Общий common.css меняет эта команда, админка передаёт пожелания.

Результат: посетитель находит кружок и расписание за три клика, все три страницы работают на данных backend на телефоне и компьютере.

## Задача 3 — Сделать рабочую админку и завершить защиту входа

Использовать существующий backend CRUD, не реализовывать его заново. Сначала согласовать простые макеты, затем сделать формы на HTML/CSS/JS. Начать с входа, списка и формы кружка; далее справочники, занятия и исключения.

Подключить login/status/logout и серверную cookie-сессию. После истечения сессии показать повторный вход; не терять несохранённый ввод в текущей странице. Не хранить пароль и флаг авторизации в localStorage.

Реализовать просмотр/создание/редактирование/удаление направлений, руководителей, аудиторий, кружков, занятий. Скрытие отделить от удаления; деструктивное действие подтверждать. Для связанных объектов показывать объяснение отказа.

Для конкретной исходной даты реализовать отмену и перенос, просмотр/изменение/удаление исключений. При переносе выбирать новую дату, время и аудиторию. После успешного сохранения перечитать данные; при 409/422 показать причину и сохранить ввод. Учитывать ответы 204 без попытки json(). Блокировать повторную отправку.

Доработать защиту: ограничение попыток входа, подходящая защита изменяющих запросов, настройка Secure-cookie для HTTPS с сохранением локального запуска, проверка выхода и срока сессии. Отсутствие кнопки не заменяет защиту API.

Где работать: frontend/admin/, frontend/js/admin/, css/admin.css; backend/app/auth.py, схемы администратора, обработчики login/logout/status и зависимости авторизации. Согласовать их API со всеми командами до изменения. Полный routers/admin.py не переписывать: доменные обработчики принадлежат задаче 1.

Результат: полный административный сценарий через браузер на реальной БД; защищённые операции и обработка ошибок; мобильные формы и проверки авторизации.

Реализовать seed из data/sample-data.json через готовые модели. Повторный запуск не создаёт дубликатов, не удаляет чужие записи и не перезаписывает данные администратора. Загрузка атомарна; ошибочные связи и значения объясняются. Для проверки использовать отдельную БД через CLUBS_SCHEDULE_DB_PATH, не рабочие данные.

Расширить корректный вымышленный набор: разные направления, комнаты и руководители, несколько занятий в неделю, скрытый кружок, отмена, перенос в другую неделю. Преднамеренно ошибочные примеры хранить отдельно. Синхронизировать браузерные моки, если они нужны разработке.

Обновить устаревшие проверки: /api/clubs уже возвращает 200, ожидание 501 неверно. Заменить skip тестами готовых функций. Восстановить независимые проверки схем/моделей и добавить приёмочные сценарии. Не ослаблять тест ради зелёного результата. До расширения набора сделать тестовую БД уникальной временной для запуска и защитить рабочую от очистки.

Проверять API, сохранение после перезапуска, Unicode-поиск, скрытые кружки, границы времени, конфликты, исключения между неделями, вход/выход/401, отсутствие файлов backend и БД в статике. В браузере проверить публичные страницы и админку, ошибки/пустые результаты, телефон, клавиатуру и длинный текст. Новые интерфейсы проверять по мере передачи; данные и API — сразу.

Провести приёмку по шести критериям README. Проверить установку в чистом venv по lock-файлу; описать запуск, seed, создание администратора, тесты и резервное копирование/восстановление SQLite. Где работать: backend/scripts/seed.py, data/, frontend/mock-data.json, backend/tests/, docs/qa-*.md, docs/START_HERE.md. README уточнять по фактическому результату. Бизнес-код и дизайн за другие команды не переписывать; найденные ошибки оформлять с воспроизведением.

## Как избежать пересечений

Задача 1 владеет доменной серверной логикой, задача 2 — публичным frontend и common.css, задача 3 — frontend админки и авторизацией, задача 4 — seed, тестовыми данными и общей приёмкой. Свои модульные тесты пишет каждая команда; файлы общего набора распределить заранее. В общем admin.py задачи 1 и 3 меняют разные функции; при переносе в отдельные модули сначала согласовать структуру.

Все начинают параллельно от существующего API и текущих моделей. Согласовать примеры 409 и изменения авторизации до интеграции. Показать по одному работающему сценарию раньше финальной сдачи; затем соединять в общей ветке через PR.
