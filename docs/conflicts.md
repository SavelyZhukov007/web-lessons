# Как считаются конфликты расписания

Цель: не дать сохранить состояние, в котором в один момент **одна аудитория** или **один руководитель** заняты двумя занятиями.

## Поток
```
запрос админа (create/update session, club, cancel, move, delete exception …)
   │  asyncio write-lock (один процесс)
   ▼
ProposedChange(operation, entity_id, payload)
   ▼
ScheduleConflictService.check_proposed_state
   1. загрузить все данные (кружки, занятия, исключения)
   2. найти «затронутые недели»: для отмен/переносов — недели original_date и new_date; для регулярных занятий — первая «обычная» неделя после текущей (без исключений) плюс все текущие/будущие недели, где есть исключения
   3. применить изменение к копии данных (в БД ещё ничего не записано)
   4. построить события этих недель (build_week: регулярные − отмены ± переносы)
   5. для событий, порождённых изменением, искать пересечения с остальными: find_conflicts
   ▼
есть конфликты → 409 {code:"CONFLICT", message, conflicts:[…]}   нет → commit
```

## Что считается конфликтом
- Одна дата, интервалы времени пересекаются как полуинтервалы `[start, end)`: «встык» (11:00 и 11:00) — **не** конфликт, вложенные и совпадающие — конфликт.
- Та же аудитория (`room`) и/или тот же руководитель (`leader`). Причины приходят в `reasons`.
- Учитывается **действующее** состояние: перенесённое занятие занимает новое время/аудиторию, а не старые.

## Что не считается конфликтом
- Отменённые занятия (они никого не занимают).
- Скрытые (`is_active = false`) кружки — их занятия в расписание не попадают.
- Занятия в разных аудиториях у разных руководителей — даже в одно время.
- Исторические недели вне затронутых — не перепроверяются (прошлое не «чинится» задним числом).

## Известные ограничения
- Защита от гонок — блокировка внутри одного процесса; для нескольких воркеров нужна БД с блокировками (см. `docs/database.md`).
- Перенос «в прошлое» разрешён намеренно (правка журнала).
- Проверяется конечный набор «представительных» недель, а не бесконечное повторение: конфликт, который возникнет только на одной конкретной далёкой неделе (из-за переноса, созданного позже), поймается при создании самого переноса.

## Примеры
| Было | Меняем | Результат |
|---|---|---|
| Пн 15:00–16:30, ауд. 101 | новое занятие Пн 16:00–17:00, ауд. 101 | 409, `reasons:["room"]` |
| Пн 15:00–16:30, ауд. 101, Иванов | новое Пн 16:00–17:00, ауд. 205, Иванов | 409, `reasons:["leader"]` |
| Пн 15:00–16:30, ауд. 101 | новое Пн 16:30–17:30, ауд. 101 | ок (встык) |
| Пн 15:00–16:30, ауд. 101 — отменено на 12.10 | новое на 12.10 15:00, ауд. 101 | ок (отменённое не занимает) |
